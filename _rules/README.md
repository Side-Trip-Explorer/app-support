# app-support 運用ルール（利用者向け文書の公開）

| 項目 | 値 |
|---|---|
| 版 | v2（2026-10-25） |
| 対象 | Side-Trip-Explorer の全アプリ（Picdule、燃費記録 など）を、iOS（Mac）と Android（Windows）で開発する Claude Code |
| 承認 | オーナー（2026-10-25） |
| 変更の記録 | `_rules/CHANGES.md` |

このファイルが運用ルールの**原本**である。`_` で始まるフォルダなので GitHub Pages では公開されない。
各プロジェクトの CLAUDE.md や手順書、ローカルの写しと食い違ったら、このファイルに従い、食い違いをオーナーに報告する。

## 1. 目的

プライバシーポリシーやサポートページなど、利用者向けの文書を1か所に集め、
アプリの実装を変えたときに、同じ流れの中で文書も実態に合わせる。

## 2. 原本と公開先

- 原本：GitHub の **Side-Trip-Explorer/app-support** リポジトリ（main ブランチ）
- 公開先：https://side-trip-explorer.github.io/app-support/ （GitHub Pages、main の / を配信）
- **各プロジェクトに控えを置かない。** 控えは必ず公開版とずれる。

## 3. 何を共通にし、何を個別にするか

文書は **アプリ×OS ごとに別** にする。共通にするのは、全アプリ・全 OS で同じものだけ。

| 区分 | 中身 | 置き場所 |
|---|---|---|
| 共通 | 共通プライバシーポリシー（アプリ名・OS 名を書かない方針だけ） | `index.html` |
| 共通 | OS を選ぶ案内ページ | `apps/<アプリ名>/index.html`、`apps/<アプリ名>/privacy/index.html` |
| 共通 | ページの構成と URL の決め方 | この文書の4章 |
| 共通 | 見た目（HTML の雛形） | `_template/privacy.html`、`_template/support.html` |
| 共通 | 更新の手順 | この文書の6章 |
| 共通 | 問い合わせ先（ikoma.datadrive@gmail.com）、コミットの名義 | この文書 |
| 共通 | 改行コード・文字コードの設定 | `.gitattributes` |
| 個別（アプリ×OS） | プライバシーポリシーの中身（保存、権限、通信、広告と SDK、保存期間と削除） | `apps/<アプリ名>/<OS>/privacy/index.html` |
| 個別 | サポートページの中身（紹介、機能、動作環境） | `apps/<アプリ名>/<OS>/index.html` |
| 個別 | ストアに登録する URL、ストアへの申告、公開する時期 | 各プロジェクトの REQ 文書 |

## 4. ページの構成と URL

| パス | 公開 URL | 区分 |
|---|---|---|
| `index.html` | https://side-trip-explorer.github.io/app-support/ | 共通 |
| `apps/<アプリ名>/index.html` | …/apps/<アプリ名>/ | 共通（OS を選ぶ案内） |
| `apps/<アプリ名>/privacy/index.html` | …/apps/<アプリ名>/privacy/ | 共通（OS を選ぶ案内） |
| `apps/<アプリ名>/<OS>/index.html` | …/apps/<アプリ名>/<OS>/ | 個別（サポートページ） |
| `apps/<アプリ名>/<OS>/privacy/index.html` | …/apps/<アプリ名>/<OS>/privacy/ | 個別（プライバシーポリシー） |

- アプリ名は小文字の英字で、iOS 版と Android 版で共通にする（`picdule`、`nenpi`）。
- OS 名は `ios` と `android` の2つに固定し、小文字にする。
- **一度公開した URL は、削除も改名もしない。** 構成を変えるときは、古い URL に新しい URL への案内ページを置く
  （GitHub Pages はサーバー側の転送ができないため）。
- **ストアには OS 別の URL を直接登録する。** 案内ページは登録しない（案内ページはポリシーとして完結していないため）。
  - プライバシーポリシー：`apps/<アプリ名>/<OS>/privacy/`
  - サポート URL（App Store）・ウェブサイト（Google Play）：`apps/<アプリ名>/<OS>/`

| アプリ | OS | 状態（2026-10-25） |
|---|---|---|
| Picdule | ios | 公開済み |
| Picdule | android | 未作成（Android のリリースの前に作る） |
| 燃費記録 | android | 未作成 |

## 5. ルール

1. **共通ページにアプリ名・OS 名を書かない。** 共通ページに書くのは、全アプリ・全 OS に当てはまる方針だけ
   （端末内に保存する方針、第三者提供の方針、問い合わせ先、改定の方針）。
   広告や SDK の名前、集める識別子、設定を変える方法は OS ごとに違うので、アプリ×OS のページに書く。
2. **アプリ×OS のプライバシーポリシーは、1枚で完結させる。** 運営者名、問い合わせ先、端末に保存するデータ、権限、
   通信先、広告と第三者の SDK、保存期間と削除、改定日を、すべてそのページに書く。共通ページに記載を委ねない
   （ストアの審査は、登録した URL のページだけを見る）。共通ページへのリンクは補足として置いてよい。
3. **自分のアプリの、自分の OS の `apps/<アプリ名>/<OS>/` の下だけを書き換える。** もう一方の OS のページには触れない。
4. **共通部分の変更は、7章の流れで行う。**
5. **書く内容はコードと設定で確かめる。** 推測で書かない。とくに次の点。
   - 通信先：`fetch(` や URL の文字列、使っている SDK（広告など）
   - 権限：app.json、iOS の infoPlist、Android のマニフェストと blockedPermissions
   - 端末に保存するもの：DB、写真の保存先、キャッシュ、OS のバックアップの対象になるか
   - 削除の動き：「削除すると消える」と書く前に、削除の処理が実際に呼ばれていることを確かめる
6. **通信・広告・権限・端末に保存するデータを変えたら、同じ変更の中でページも直す。**
7. **ページを直したら、自分の OS のストアへの申告と突き合わせる。**
   Android は Play Console のデータセーフティ、iOS は App Store Connect の「App のプライバシー」。
   一致しなければ、変える項目と回答の案をオーナーに渡す（ストアへの入力はオーナーが行う）。
8. **ページは、その内容を含む版をストアの審査に出す前に公開する。**
9. **プッシュの前に、毎回オーナーに差分を見せて OK をもらう。** 公開ページは誰でも読めるため。

## 6. 更新の手順

1. **最新を取得する。** 作業用コピーはプロジェクトの外に、**アプリごとに別に**置く（`<アプリ名>` は `picdule`、`nenpi` など）。
   同じコピーを別のアプリのセッションと使うと、相手のローカルのコミットが自分の push に混ざる（2026-10-26〜27 に2回起きた）。

   | 環境 | 作業用コピーの場所 |
   |---|---|
   | Mac（zsh） | `~/.cache/side-trip-explorer/app-support-<アプリ名>` |
   | Windows（Git Bash） | `$HOME/.cache/side-trip-explorer/app-support-<アプリ名>` |
   | Windows（PowerShell） | `$env:USERPROFILE\.cache\side-trip-explorer\app-support-<アプリ名>` |

   無ければ `gh repo clone Side-Trip-Explorer/app-support <場所>`、あれば `git pull`。
   未プッシュのコミットや未コミットの変更が残っていたら、先にオーナーに知らせる。
2. **このファイルと `_rules/CHANGES.md` を読む。** 前回から増えた行に、自分の OS で対応が要るものがあれば、
   オーナーに知らせてから作業する。
3. **作業用コピーの設定を確かめる**（初回だけ）。
   ```
   git config user.name Side-Trip-Explorer
   git config user.email ikoma.datadrive@gmail.com
   git config core.autocrlf false
   ```
   `gh auth status` で、Side-Trip-Explorer に書き込めるアカウントでログインしていることを確かめる。
4. **実態を確かめる**（5章のルール 5）。
5. **書き換える。** 新しいページは `_template/` の雛形を写して作り、`{ }` の印をすべて埋める。
   変えたページの「最終更新日」を、日本時間の今日にする。
   ファイルは UTF-8（BOM なし）、改行 LF で保存する。Claude の Edit／Write ツールで書き、
   PowerShell のリダイレクト（`>`、`Out-File`、`Set-Content`）では書かない。
6. **範囲を検査する。**
   ```
   git status --porcelain
   ```
   出てきたファイルが、すべて `apps/<アプリ名>/<OS>/` の下であることを確かめる（新しいファイルもここに出る）。
   外のファイルがあれば止める。
7. **ローカルでコミットする。** 件名は英語の命令形、本文は何を・なぜ。
8. **オーナーに見せる。** `git log --oneline origin/main..HEAD` と `git diff origin/main` を要約して見せ、
   プッシュの OK をもらう。`git log origin/main..HEAD` の**全行が自分のアプリのコミット**であることも確かめる。
9. **プッシュの直前に取り込む。** `git pull --rebase`。取り込んだ変更があれば、手順 6 と 8 をやり直す。
10. **プッシュして確かめる。** `git push` の後、数分おいて公開ページを開き、
    最終更新日と変更した文が反映されたことを確かめる（GitHub Pages の反映には時間がかかる）。
11. **ストアへの申告と突き合わせる**（5章のルール 7）。
12. **プロジェクト側に記録する。** 関係する REQ 文書に、app-support のコミット、公開 URL、日付、
    ストアへの申告を変えたかどうかを書く。

## 7. 共通部分を変えるとき

共通部分（3章で「共通」としたもの。この文書自体も含む）は、次の流れで変える。

1. どちらの OS の Claude も提案できる。提案には、変更の理由と、影響を受けるアプリ×OS のページの一覧を付ける。
2. オーナーが承認する。
3. 共通部分の変更は、アプリ×OS のページの変更とは別のコミットにする。
   同じコミットで `_rules/CHANGES.md` に「日付、変更点、もう一方の OS で必要な対応」を1行足す。
4. 共通部分の変更のついでに、もう一方の OS のページを直さない。対応はもう一方の OS の Claude が行う。

案内ページ（`apps/<アプリ名>/index.html` と `apps/<アプリ名>/privacy/index.html`）に、
新しい OS のページへのリンクを足すことも、共通部分の変更として扱う。
